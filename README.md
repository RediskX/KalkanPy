# KalkanPy — ЭЦП НУЦ РК на чистом Python

Независимая реализация проверки и формирования электронной подписи Республики Казахстан (pki.gov.kz) **без** бинарных библиотек НУЦ
(`KalkanCrypt.dll`, `libkalkancryptwr*.so`, NCALayer). Python 3, на открытых библиотеках: `gostcrypto` (Стрибог, ГОСТ Р 34.10-2012/2015),
`asn1crypto` (ASN.1: X.509, CMS), `cryptography`, `pycryptodome`, `lxml`.

* **Алгоритмы:** ГОСТ 34.10-2015 / Стрибог (256 и 512 бит), устаревшие СТ РК ГОСТ Р 34.310-2004 / 34.311 (реализованы с нуля), RSA-SHA256.
* **Форматы:** X.509 и цепочки до корня НУЦ, CMS/CAdES-BES, RAW-подпись, PKCS#12 (`.p12` НУЦ), XMLDSig, WS-Security (WSSE),
  метка времени RFC 3161, CRL и OCSP, ZIP-контейнеры (ZipCon), токены PKCS#11 (каркас).
* **Интерфейс как у Калкана:** функции `SignData`/`VerifyData`/`SignXML`/`VerifyXML`, флаги `KC_*`, кодировки входа и выхода,
  свойства сертификата `KC_CERTPROP_*` — результаты сверены с настоящей `KalkanCrypt.dll` в обе стороны.

> Не является сертифицированным средством криптографической защиты информации и не связан с АО «НУЦ РК».

## Конфигурация и приватность

В репозитории нет ключей, паролей и персональных данных. Всё, что относится к вашему компьютеру, задаётся **переменными окружения**
или локальным файлом `local_keys.py` (он в `.gitignore`):

| Переменная | Назначение |
|---|---|
| `KALKAN_DIR` | каталог с тестовыми `GOST512_*.p12` и корнями НУЦ (`root_gost_2022.cer`, `nca_gost_2022.cer`) |
| `KALKAN_P12_PASSWORD` | пароль контейнера (по умолчанию — часть имени файла после последнего `_`) |
| `KALKAN_SDK_DIR` | каталог данных SDK НУЦ РК («SDK 2.0») для сверочных скриптов |
| `KALKAN_DLL` | путь к `KalkanCrypt.dll` для сверки с оригиналом |
| `KNCA_PKCS11` | модуль PKCS#11 |
| `KALKAN_SHOW_PII=1` | показывать персональные данные из сертификатов (по умолчанию в выводе они маскируются) |

Если ключей или SDK нет, сверочные скрипты печатают `SKIP` и не падают: сама библиотека от них не зависит.
Пример `local_keys.py`: `DIR = r"C:\keys"`, `SDK_DIR = r"C:\sdk\SDK 2.0"`.

## Что доказано на образцах SDK (✔ — подтверждено прогоном)

Тестовые данные: `Keys and Certs\CA_Test\ROOT\root_test_gost_2022.cer`,
`...\NCA\nca_gost2022_test.cer`.

1. **Кривая 512-бит.** Открытый ключ в SPKI — 128 байт (X‖Y по 64);
   подпись сертификата — 128 байт. Это ГОСТ Р 34.10-2015 (512-бит), кривая
   `paramSetA`.
2. **OID НУЦ 2015 (ветка `1.2.398.3.10.*`, НЕ российская ТК26 `1.2.643.7.*`):**
   - `1.2.398.3.10.1.1.2.2`   — открытый ключ ГОСТ 2015;
   - `1.2.398.3.10.1.1.2.2.1` — хэш ГОСТ Р 34.11-2015 (Стрибог);
   - `1.2.398.3.10.1.1.2.3.2` — подпись ГОСТ Р 34.10-2015.
3. **Формат точки ключа** — OCTET STRING внутри BIT STRING: `04 81 80 <X‖Y>`.
4. **Порядок байт (стиль RFC 4491, little-endian):**
   - координаты ключа X‖Y — каждая половина little-endian;
   - подпись r‖s      — каждая половина little-endian;
   - хэш Стрибог      — результат разворачивается (little-endian).
   Именно эта тройка даёт валидную проверку; прочие комбинации — False.
5. **Устаревшие алгоритмы** (legacy «GOST 2004», тест-сертификаты/CMS НУЦ):
   - `1.2.398.3.10.1.1.1.1` — подпись СТ РК ГОСТ Р 34.310-2004 (≈ 34.10-2001) в CMS;
   - `1.2.398.3.10.1.1.1.2` — та же подпись в сертификате;
   - `1.2.398.3.10.1.3.1`   — хэш   СТ РК ГОСТ Р 34.311 (≈ 34.11-94).
   Параметры кривой лежат в SPKI (KeyParams): `1.2.398.3.10.1.1.1.1.1` = набор A
   (совпадает с CryptoPro-A), ключ — 64 байта X‖Y (little-endian), подпись — 64 байта r‖s
   (little-endian), хэш — 32 байта в обратном порядке (казахстанская презентация).
   Реализовано с нуля в `kalkan_legacy.py`; сверено с `pygost`, RFC 5831 и `KalkanCrypt.dll`,
   а также проверено на реальных объектах (`test_legacy.py`).

## API

```python
from kalkan_verify import verify_certificate, verify_certificate_chain, verify_cms
from kalkan_sign import (create_self_signed_certificate, raw_sign, raw_verify,
                         sign_cms)

# --- проверка ---------------------------------------------------------------
ok  = verify_certificate(leaf_der, issuer_der)          # подпись сертификата
ok  = verify_certificate_chain([nca_der], root_der)     # цепочка до корня
res = verify_cms(open("file.cms", "rb").read())         # подписанное сообщение

# --- создание (нужен приватный ключ ГОСТ 2015) ------------------------------
cert = create_self_signed_certificate(priv, "MY GOST2015")   # DER сертификата
raw  = raw_sign(priv, data)                                   # RAW-подпись
ok   = raw_verify(raw, data, cert)                            # проверка RAW
cms  = sign_cms(priv, data, cert, detached=False)             # CMS с сертификатом
ok   = verify_cms(cms)["signers"][0]["state"] == "ok"

# --- контейнеры ZipCon (аналог ZipConSign/ZipConVerify) ---------------------
from kalkan_zipcon import sign_zipcon, verify_zipcon
sign_zipcon(["a.txt", "b.bin"], priv, cert, "out.zip")        # манифест + CMS
rep = verify_zipcon("out.zip")                                # отчёт по файлам и подписям
ok  = rep["ok"] and not rep["problems"]
```

## Кросс-проверка с вендорской библиотекой (`cross_check_dll.py`)

Обе стороны, RAW и CMS — **ВСЁ ОК** на реальных ключах:

```
A) Калкан RAW -> мой raw_verify   : True
A) Калкан CMS -> мой verify_cms   : ok
B) мой RAW   -> Калкан VerifyData : True (rc=0x00000000)
B) мой CMS   -> Калкан VerifyData : True (rc=0x00000000)
```

Три условия, без которых у вендора ничего не сходится (определены экспериментально,
подтверждены рабочим кодом обёртки):

1. **Порядок инициализации.** `Init → LoadKeyStore → X509LoadCertificateFromFile(root, KC_CERT_CA)
   → X509LoadCertificateFromFile(nca, KC_CERT_INTERMEDIATE)`. Сертификаты УЦ грузятся **после**
   ключа; если грузить до — `KCR_CACERTNOTFOUND (0x8F000040)`. (Windows-хранилище тут ни при чём —
   достаточно этих двух вызовов.)
2. **Флаги RAW.** Формирование: `KC_SIGN_DRAFT + InFlags + outFlags`.
   Проверка: `KC_SIGN_DRAFT | KC_IN_BASE64` (0x11), подпись — **base64**.
   `KC_IN2_BASE64` даёт `BASE64_DECODE_ERROR`, а флаг без base64 роняет DLL — не использовать.
3. **Свежий контекст на каждый `VerifyData`.** DLL хранит состояние: повторные/разнотипные
   вызовы в одном контексте дают ошибки движка (`0x0D06B08E`, `0x8006E07B`). Для нескольких
   проверок — `Finalize` и заново `Init`/`LoadKeyStore`/CA.

Флаги CMS: формирование `KC_SIGN_CMS + KC_WITH_CERT + InFlags + outFlags`; проверка — `KC_SIGN_CMS`.

## Кодировки вход/выход (как у Калкана)

`kalkan_api.py` повторяет «стену флагов» KalkanCryptCOM и сверен с DLL (`cross_check_formats.py`):

| | вход | выход |
|---|---|---|
| RAW | текст (без флага), `KC_IN_BASE64`, `KC_IN_FILE` | `KC_OUT_BASE64` → base64; `KC_OUT_DER`/`KC_OUT_PEM` → сырые 128 б |
| CMS | текст, `KC_IN_BASE64`, `KC_IN_PEM` (`-----BEGIN CMS-----`), `KC_IN_FILE` | `KC_OUT_BASE64`; `KC_OUT_DER`; `KC_OUT_PEM` → `-----BEGIN CMS-----` (строки по 64) |
| detached | `KC_DETACHED_DATA` | CMS без содержимого |

Важно для CMS: `digestAlgorithm` у Калкана для 512-битного ключа — `1.2.398.3.10.1.3.3`
(не `…2.2.1`); при несовпадении base64-ветка проверки даёт `verify error`. CMS включает атрибут
CAdES-BES **`signingCertificateV2`** (OID `1.2.840.113549.1.9.16.2.47`):
`SEQUENCE{ SEQUENCE{ SEQUENCE{ OCTET STRING } } }` с `certHash = SHA-256(сертификата)` и
**опущенным** `hashAlgorithm` (default) — именно так, как у Калкана. Калкан принимает такую CMS
во всех форматах (DER/base64/PEM/detached).

## XMLDSig: URI и форматы как у Калкана

Снято с вывода настоящего `KalkanCrypt.dll` (`SignXML`):

```
SignatureMethod : urn:ietf:params:xml:ns:pkigovkz:xmlsec:algorithms:gostr34102015-gostr34112015-512
DigestMethod    : urn:ietf:params:xml:ns:pkigovkz:xmlsec:algorithms:gostr34112015-512
Transforms      : enveloped-signature + C14N WithComments
DigestValue/SignatureValue/X509Certificate — base64 со строками по 64 символа
```
`sign_xml` (фасад и `kalkan_xmldsig`) повторяет это; проверка `verify_xml` читает трансформы
(WithComments учитывается). Оба направления сверены с DLL (`cross_check_xml.py`).




## Внутренности `.p12` НУЦ (разобрано)

```
Pfx (v3)
├─ authSafe (data)
│  ├─ ContentInfo data          → pkcs8ShroudedKeyBag  (PBE-SHA1-3DES)
│  └─ ContentInfo encryptedData → certBag              (pbeWithSHAAnd40BitRC2-CBC)
└─ macData: SHA-1, salt(20), iterations, MAC = HMAC-SHA1(KDF(id=3), authSafeContent)
```
Особенности, из-за которых обычные библиотеки пасуют: **BER с неопределённой длиной** внутри
(`30 80 ... 00 00`), **RC2-40** для сертификата и пароль в BMPString.
Пароль тестовых ключей НУЦ — суффикс имени файла после последнего `_`.



## Контейнеры ZipCon (аналог `ZipConSign`/`ZipConVerify`)

Формат разобран на реальных контейнерах НУЦ и на контейнере, собранном самой DLL:

```
ZIP:
├─ <подписанные файлы>
├─ META-INF/NCAManifest.xml        манифест (SigReference + DataObjectReference)
└─ META-INF/signature-<id>.cms     CMS по БАЙТАМ манифеста (detached, id-data)
```

Манифест печатается ровно как у вендора (проверено побайтовым сравнением):

```
<?xml version="1.0" encoding="UTF-8" standalone="yes"?> \r\n   ← пробел после "?>"
<NCAManifest>\r\n
\t<SigReference URI="META-INF/signature-ab12cd34ef.cms"/>\r\n
\t<DataObjectReference URI="файл">\r\n
\t\t<DigestMethod Algorithm="urn:ietf:params:xml:ns:pkigovkz:xmlsec:algorithms:gostr34112015-512"/>\r\n
\t\t<DigestValue>base64</DigestValue>\r\n
\t</DataObjectReference>\r\n
</NCAManifest>                                                  ← без завершающего \r\n
```

Наблюдения, снятые с вендорских контейнеров:

* дайджест файла `gostr34112015-512` = наш `streebog(data, 64)` (KZ-презентация) — совпал 5/5
  на реальном контейнере и на всех контейнерах, собранных DLL;
* устаревшие контейнеры используют `…#gost34311` → наш `gost341194_kz`, а по подписи —
  ГОСТ 34.10-2001 (см. раздел про legacy-ГОСТ);
* `signatureAlgorithm` в CMS может быть `rsaEncryption` (1.2.840.113549.1.1.1) — тогда хеш
  берётся из `digestAlgorithm`; верификатор это принимает;
* **DLL кладёт `NULL` в параметры `digestAlgorithm`** (`30 0c 06 08 …03 03 05 00`). Без этого
  `ZipConVerify` отвечает «CMS Verify - FAILED», хотя обычный `VerifyData` такой CMS принимает.
  Мы печатаем `NULL` — и наш контейнер DLL принимает (`rc=0`, «CMS Verify - OK»);
* `DigestValue` для файла, имя которого из манифеста нужно искать в архиве буквально —
  имена в ZIP хранятся как есть, а имя файла подписи DLL ищет по `SigReference/@URI`
  (несовпадение даёт `KCR_FILEREADERROR`, а не «подпись неверна»);
* `signature-<id>` не выводится из содержимого (не CRC/MD5/SHA-хеш): у двух прогонов DLL
  разные значения → произвольный идентификатор, не влияет на проверку.

**Не-ASCII имена файлов.** Windows-версия вендора хранит имена в ZIP как ANSI (cp1251)
без флага UTF-8, а манифест при этом печатает с `encoding="UTF-8"` — то есть байты в нём
cp1251. Наши функции это переживают: `parse_manifest` при ошибке разбора UTF-8 повторяет
разбор как cp1251, а `verify_zipcon` сопоставляет URI из манифеста с записями архива
не только буквально, но и по «сырым» байтам имени. **Сама DLL** кириллицу не переваривает:
на нашем контейнере с кириллическим именем она отвечает `KCR_XMLPARSEERROR` (0x08f00026),
а её собственный `ZipConSign` с ANSI-путём вообще завершается с `rc=0x08f0001f`, не записав
манифест. Поэтому для обмена с вендором имена файлов лучше держать в ASCII (транслитерация).

Проверка (`verify_zipcon`) возвращает отчёт с отдельными блоками `files`/`signatures`
и списком `problems`: видно, что именно разошлось — файл, дайджест или подпись.
Образцы ZipCon из SDK **не проходят** проверку и у самой DLL (манифест, судя по всему,
пересобирали после подписания), поэтому эталоном служит контейнер, собранный DLL заново.


## Токены (PKCS#11)

`kalkan_pkcs11.py` напрямую работает с PKCS#11-драйвером носителя; приватный ключ
**не покидает токен** — подпись считает `C_Sign`, а наш верификатор её проверяет.

```python
from kalkan_pkcs11 import Pkcs11Token
from kalkan_sign import raw_verify

token = Pkcs11Token(r"...\knca_pkcs11.dll")   # модуль PKCS#11 носителя
token.initialize()
for slot in token.slots(token_present=True):
    print(slot, token.token_info(slot))

token.open_session(slot)
token.login("123456")                          # PIN пользователя

certs = token.find_certificates()              # CKO_CERTIFICATE (DER в certificate_der)
keys = token.find_private_keys()               # CKO_PRIVATE_KEY (CKA_ID)
signature = token.sign(data,
                       mechanism=Pkcs11Token.CKM_GOSTR3410_WITH_GOSTR3411,
                       key_id=certs[0]["id"])  # токен хэширует сам
assert raw_verify(signature, data, certs[0]["certificate_der"])

signature = token.sign_raw(data, size=64, key_id=certs[0]["id"])
assert raw_verify(signature, data, certs[0]["certificate_der"])

# CMS: токен подписывает signedAttributes, контейнер (CAdES-BES) собираем сами
cms = token.sign_cms(data, certs[0]["certificate_der"], key_id=certs[0]["id"])
assert verify_cms(cms)["signers"][0]["state"] == "ok"
token.finalize()
```

Проверка цикла: `python test_pkcs11.py`.
Часть 1 гоняет полный цикл (init → slots → session → login → find → `C_Sign`) на
**мок-модуле** без железа и подтверждает подпись нашим `raw_verify`, а CMS — `verify_cms`;
часть 1b проверяет устойчивость к атрибутам, которых носитель не отдаёт; часть 2 пробует
реальный модуль (по умолчанию `knca_pkcs11.dll` из SDK, либо `KNCA_PKCS11=<путь>`, например SoftHSM2).

Есть `token.mechanisms()` (`C_GetMechanismList`) — покажет, что реально поддерживает носитель,
и `with token.session(slot, pin=...)` — сессия закрывается даже при исключении.

Механизм подписи у разных носителей отличается (`CKM_GOSTR3410` = 0x1201 либо
`CKM_GOSTR3410_WITH_GOSTR3411` = 0x1202) — он задаётся параметром `mechanism`.

**Честно о границах проверки.** Мок не может подтвердить то, что зависит от железа:
порядок байт на выходе `C_Sign` (мы ожидаем `r‖s`, каждая половина little-endian — как у НУЦ)
и то, что константы механизмов у конкретного носителя означают именно редакцию 2015 для
Стрибог-256/512. Это первое, что нужно проверить на живом токене или SoftHSM2:
сначала `token.mechanisms()`, затем `sign_raw` + `raw_verify`, затем сверка CMS с `KalkanCrypt.dll`.


## Область охвата и ограничения (честно)

- **Доверие.** `verify_cms` по умолчанию проверяет только криптографию (digest + подпись); передайте
  `trust_anchor_der` (цепочка) и `check_time` (срок) — результаты в `chain_ok`/`time_ok`.
  **Отзыв — отдельно**: `kalkan_revoke.check_crl` (CRL) и `kalkan_revoke.ocsp_check` (OCSP); в `verify_cms` не встроены.
- **Алгоритмы.** ГОСТ 2015 (СТ РК ГОСТ Р 34.10/34.11-2015), RSA
  (sha256WithRSAEncryption/SHA-256) и **устаревшие ГОСТ** СТ РК 34.310-2004/34.311-95
  (28147-89 + 34.11-94 + 34.10-2001, `kalkan_legacy.py`) — проверены на реальных
  сертификатах и CMS НУЦ. На объектах НУЦ встречается набор кривой A (=CryptoPro-A,
  OID `1.2.398.3.10.1.1.1.1.1`); наборы B/C поддержаны кодом, но их привязка
  (`.2 → B`, `.3 → C`) на реальных объектах **не подтверждена**. Наборы параметров
  хэша: НУЦ использует тестовый (подтверждено по DLL); набор КриптоПро реализован
  и сверен с `pygost`, но в объектах НУЦ не встречался.
  Не реализованы: устаревшая *подпись* ГОСТ Р 34.10-94 (не 2001) и наборы параметров
  хэша с ненулевым начальным вектором.
- **Строгость CMS.** Подписанные атрибуты разбираются по RFC 5652 (§5.3/§11.2): повтор
  имени атрибута, несколько значений `message-digest`, отсутствие или несовпадение
  `content-type` с типом содержимого → не `ok` (соответствующий `state`). Legacy-подписи
  без `signedAttrs` проверяются по самому содержимому (так умеет старый Калкан).
- **Отказ вместо исключений.** Проверка подписи 34.10-2001 на негодных входах (длины,
  диапазоны, точка не на кривой, бесконечность) возвращает `False`; неизвестный набор
  параметров кривой — `UnsupportedAlgorithm`. Цепочка (`verify_certificate_chain`) и
  `verify_cms` на битом входе возвращают отказ, а не падают; один негодный подписант
  получает `state = "error: …"` и не рушит разбор остальных. Прямой вызов
  `verify_certificate` с неразбираемым DER всё же поднимает `ValueError` (это ошибка
  вызывающего, о чём сказано в докстроке).
- **Контейнеры.** Читается `.p12` с PBE-SHA1-3DES (ключ) и RC2-40 (сертификат); другие PBE (PBES2/AES) — нет.
  Устаревшие контейнеры НУЦ (`GOSTKNCA_*.p12`) не открываются: пароль тестовых файлов
  неизвестен, а MAC таких контейнеров может считаться по ГОСТ 34.11-94 (проверить нечем).
- **Токены** (Kaztoken/eToken/JaCarta/aKey, ID-карта) — через PKCS#11 (`kalkan_pkcs11.py`).
  Цикл проверен на мок-модуле; на реальном железе нужен PKCS#11-модуль носителя
  (учтите: `knca_pkcs11.dll` из SDK НУЦ — **не** PKCS#11-модуль: он не экспортирует `C_GetFunctionList`).
- **ZipCon-контейнеры.** Проверка — полностью (манифест, дайджесты `…#gost34311`
  (устаревший ГОСТ) и Стрибог-256/512, подписи по байтам манифеста, несколько подписей).
  Сборка — одной подписью на ключе ГОСТ 2015 (512/256) либо любом локальном ключе;
  добавление второй подписи к существующему контейнеру не реализовано (DLL это умеет,
  но у нас не проверено).
  Замечено при разборе: **образцы ZipCon из SDK не проходят проверку и у самой DLL**
  (`CMS Verify - FAILED`, `GOST_EC_VERIFY: signature mismatch`) — похоже, манифест
  пересобирали после подписи; дайджесты файлов в них при этом верны. Поэтому положительным
  эталоном служит не образец, а контейнер, собранный DLL с реальным ключом.
- **TSA**: токен запрашивается, разбирается и **криптографически проверяется** (`kalkan_tsa.verify_timestamp_token`):
  подпись TSA (RSA/ГОСТ) + digest, `messageImprint` против данных, `nonce`, EKU=timeStamping; цепочка TSA — опционально (`trust_anchor_der`).
- **WSSE**: реализован, самопроверен и сверен с вендорским `SignWSSE` (направление «вендор → мы», с негативами);
  обратное направление невозможно: в интерфейсе `KalkanCrypt.dll` нет `VerifyWSSE` (только `VerifyXML`).
- Проверено на двух реальных ключах ГОСТ-512; ГОСТ-256 — на синтетике; RSA — на синтетике.

## Важно

- Подписи, сформированные своим кодом, **математически совместимы** с НУЦ РК,
  но библиотека **не является сертифицированным КУЦ**. Там, где система-приёмник
  требует именно сертифицированный провайдер, формального статуса не будет.
- Токены (Kaztoken/eToken/JaCarta/aKey) держат ключ в железе — для них нужен
  PKCS#11-драйвер устройства; полностью «чистым Python» это не решается.
- Лицензии зависимостей: gostcrypto (MIT), asn1crypto (MIT).


## Устаревшие ГОСТ (реализованы с нуля)

Поддерживается устаревший стек СТ РК ГОСТ Р 34.310-2004 / 34.311-95
(≈ ГОСТ Р 34.10-2001 / 34.11-94). Новый модуль `kalkan_legacy.py` — полностью своя
реализация (внешних ГОСТ-94/2001 библиотек нет):

* **ГОСТ 28147-89** — блочный шифр: подстановки, функция `g`, расписание подключей;
* **ГОСТ Р 34.11-94** (СТ РК 34.311-95) — 256-битный хэш: преобразования `A`, `P`,
  регистр `χ`, 61 цикл, шаговая функция сжатия;
* **ГОСТ Р 34.10-2001** (СТ РК 34.310-2004) — проверка подписи на эллиптической
  кривой (наборы A/B/C, RFC 4357).

Как это сверено (воспроизводится `python test_legacy.py`):

| Проверка | Эталон | Результат |
|---|---|---|
| Ядро 28147-89 | Magma из `gostcrypto`: вектор ГОСТ Р 34.13-2015 + 20 случайных пар в тесте (при разработке 50) | 0 расхождений |
| Хэш 34.11-94 | `pygost` 0.15, если установлен: таблицы **обоих** наборов сверяются построчно с его встроенными, затем 32 входа × 2 набора (без подмены таблиц) | 0 расхождений |
| Шаговая функция | промежуточные `K1`, `K2`, `KSI` из RFC 5831 (§7.3.1, STEP 3) | совпало |
| Закон группы кривой | `q*G = ∞`, `2G = G+G`, `G+(-G) = ∞` (набор A) | выполняется |
| Офлайн-вектор 34.10-2001 | свой ключ → своя подпись → проверка (без SDK) | принимает; подделки — нет |
| Хэш в KZ-презентации | `HashData("Gost34311_95")` из `KalkanCrypt.dll` | совпало побайтово |
| Подпись 34.10-2001 | самоподпись корневого legacy-сертификата НУЦ | проходит |
| Цепочка | сертификат НУЦ под корнем; негативы: «сам за себя», порча байта | проходит / отвергается |
| CMS | `test_CMS_GOST.txt` из SDK: digest + signedAttrs + подпись | `state = ok` |

Негативные регрессы: подпись для «ключа» Q = −G, нулевой/пустой
открытый ключ, точка не на кривой, подпись не 64 байта, пустой хэш — всё отвергается
(`False`, без исключений). Ранее два первых случая **принимались** — это была реальная
ошибка: не проверялся закон группы (бесконечность) и валидность точки ключа.

Закреплённые конвенции КЗ (определены перебором и проверены на реальных объектах):

* хэш 32 байта — результат 34.11-94 в **обратном порядке байт** (`gost341194_kz`);
  для пустого ввода KalkanCrypt всегда обрабатывает хотя бы один нулевой блок (учтено);
* ключ SPKI — 64 байта `X‖Y`, половины little-endian; подпись — 64 байта `r‖s`
  (little-endian); параметры кривой — в KeyParams, OID `1.2.398.3.10.1.1.1.1.1` = набор A
  (совпадает с CryptoPro-A `1.2.643.2.2.35.1`);
* в CMS подпись считается по `signedAttrs` (SET с тегом `0x31`), как в RFC 5652;
* тестовый `test_CMS_GOST.txt` из SDK и legacy-сертификаты НУЦ больше не помечаются
  `unsupported_legacy` — они проверяются полностью (`state = ok`).

Проверка правок: `python test_legacy.py` (0 при успехе; без SDK/DLL печатает SKIP).
